# Rig-A2A

Agent-to-Agent (A2A) protocol client integration for [Rig](https://github.com/0xPlaygrounds/rig).

`A2AClient` connects to any [A2A](https://a2a-protocol.org)-compliant agent by
fetching its well-known `AgentCard`, then exposes that agent two ways: as a
**tool** a local Rig agent can call, or as a **completion model** backing a Rig
agent directly.

`rig-a2a` currently supports native targets. The upstream A2A client uses Tokio
networking, which is not available on `wasm32-unknown-unknown`.

## Installation

Add the companion crate to your `Cargo.toml`, along with the rig-core crate:

```toml
[dependencies]
rig-a2a = "0.41.0"
rig-core = "0.41.0"
```

You can also run `cargo add rig-a2a rig-core` to add the most recent versions
of the dependencies to your project.

The root `rig` facade also exposes this crate behind the `a2a` feature, at the
module path `rig::a2a`.

## Feature flags

| feature      | default | enables                                  |
|--------------|---------|------------------------------------------|
| `rustls`     | yes     | rustls TLS for the HTTP transport        |
| `native-tls` | no      | native-tls for the HTTP transport        |

The JSON-RPC and REST HTTP bindings are wired up. The client selects the first
supported interface in the order advertised by the remote `AgentCard`, and
copies that interface's optional `tenant` into each request as required by A2A.
Agent-card discovery and protocol requests have a five-minute default timeout.
Use `A2AClient::builder().timeout(...)` to override it.

## The remote agent as a tool

`A2AAgentBuilderExt::a2a_tool` binds the remote agent to a local Rig agent:

```rust,no_run
use rig_core::providers::openai;
use rig_core::client::{CompletionClient, ProviderClient};
use rig_agent::client::AgentClientExt;
use rig_agent::completion::Prompt;
use rig_a2a::{A2AAgentBuilderExt, A2AClient};

# async fn run() -> anyhow::Result<()> {
let client = openai::Client::from_env()?;
let remote = A2AClient::from_url("http://localhost:8080").await?;

let agent = client
    .agent(openai::GPT_5_2)
    .a2a_tool(&remote)
    .build();

let reply = agent.prompt("Greet me.").await?;
println!("{reply}");
# Ok(()) }
```

**One remote agent becomes one tool**, taking a single `prompt` argument — the
same shape `Agent::into_tool()` gives a sub-agent. The A2A protocol routes every
request through the same `message/send` endpoint and carries no skill selector,
so the skills a card declares are not separately callable; they are rendered
into the tool's description as documentation.

The tool takes its name from the remote's card. Two remotes whose card names
slug identically collide, and Rig's registry keeps only the last registration —
set `A2AClient::builder().tool_name(...)` when connecting to several.

## The remote agent as a model

`A2AClient::agent` builds a Rig `Agent` whose completions *are* A2A requests, so
`prompt`, `chat`, streaming, hooks, and conversation memory all work against a
remote agent with no LLM provider involved:

```rust,no_run
use rig_agent::completion::Prompt;

# async fn run(client: rig_a2a::A2AClient) -> anyhow::Result<()> {
let agent = client.agent().build();
let reply = agent
    .prompt("Summarize our discussion.")
    .conversation("user-42")
    .await?;
# let _ = reply;
# Ok(()) }
```

One agent serves every conversation: `A2AClient::agent` registers
`A2AThreadHook`, which carries the run's conversation id to the model.

A `CompletionRequest` describes a chat-completion API, and A2A is a different
contract — it exchanges messages with an agent that owns its instructions and
hides its tools. `A2AModel` refuses, rather than silently ignores, the request
fields whose absence would change the result:

| Request field | Behavior |
|---|---|
| `tools` | **Error** — a remote agent never returns a tool call, so registering local tools would advertise tools that can never be invoked. |
| `output_schema` | **Error** — A2A cannot constrain remote output, so extraction would return unvalidated text. |
| `tool_choice` | **Error** when it demands a tool; ignored when it merely permits one. |
| `preamble` | Sent as a leading text part; the remote may disregard it. |
| `documents` | Sent as one text part each. |
| `temperature`, `max_tokens`, `additional_params`, `model` | Ignored — sampling belongs to the remote agent. |

Usage is reported as zero, Rig's documented sentinel for "no metrics supplied";
A2A has no token accounting.

## Conversation threading

Per the [A2A specification](https://a2a-protocol.org/latest/specification/),
`contextId` and `taskId` are generated by the server and echoed back by clients.
This crate never shows them to a model. Instead the host records the identifiers
issued for each `ConversationId` and re-attaches them, so a model can neither
forge an identifier nor lose one:

```rust,no_run
use rig_agent::completion::Prompt;

# async fn run(agent: rig_agent::agent::Agent) -> anyhow::Result<()> {
let reply = agent
    .prompt("And what did I ask you first?")
    .conversation("user-42")                                // Rig-side memory
    .tool_context(rig_a2a::conversation_context("user-42")) // remote A2A thread
    .await?;
# let _ = reply;
# Ok(()) }
```

The two identifiers are independent knobs — Rig will not reconcile them, so pass
the same string to both if you want a Rig conversation and its remote
counterpart to stay aligned. On the model surface `.conversation(...)` covers
both, because `A2AThreadHook` forwards it to `A2AModel`.

If you keep the server-issued ids yourself, supply them per request instead and
the client's own tracking is bypassed:

```rust,no_run
use rig_agent::completion::Prompt;
use serde_json::json;

# async fn run(agent: rig_agent::agent::Agent, context_id: String) -> anyhow::Result<()> {
let reply = agent
    .prompt("Continue where we left off.")
    .merge_additional_params(
        json!({ "a2a": { "context_id": context_id } })
            .as_object()
            .cloned()
            .unwrap_or_default(),
    )
    .await?;
# let _ = reply;
# Ok(()) }
```

Threading rules:

- The server-issued `contextId` is recorded for every response, including
  failures, so a failed turn does not drop the conversation.
- A `taskId` is retained **only** for a task paused in `input-required`, the one
  state where a follow-up message is well defined. Re-sending to a `working` or
  `submitted` task draws "task execution is already in progress", and a terminal
  `taskId` makes the server replay the stale task.
- A task paused in `input-required` surfaces as `[a2a input-required] <prompt>`;
  the next call in that conversation resumes it automatically.
- Without a `ConversationId`, every call is an independent single-turn exchange.
- Conversations are tracked per client, bounded, and evicted least-recently-used;
  an evicted key simply starts a new remote conversation.
- Reading and recording are not atomic, so concurrent calls under one
  `ConversationId` race and the later write wins. Serialize calls that must
  share a conversation.

The direct `A2AClient::message` API is the exception: it stays explicit and
threads only the identifiers you hand it.

## Remote failures

A task the remote failed, rejected, cancelled, or gated behind authentication
returns a typed `ToolExecutionError` rather than text, so the kind reaches hooks
and telemetry. The remote's own status message is the error text and is what the
model sees:

| Task state | Tool error |
|---|---|
| `failed` | `ToolErrorKind::Provider` |
| `rejected` | refusal (`ToolErrorKind::PermissionDenied`) |
| `canceled` | `ToolErrorKind::Cancelled` |
| `auth-required` | `ToolErrorKind::PermissionDenied` |

## Observing the remote identifiers

Every tool call that reaches the remote publishes an `A2AThreadInfo` through
`ToolContext::insert_result`, including one whose task came back failed. A call
rejected before it is sent (invalid arguments) or one that fails in transport
has no identifiers to publish. Hooks read it off
`ToolResultEvent::tool_context`; it never reaches the model.

```rust
use rig_a2a::A2AThreadInfo;
use rig_agent::agent::{AgentHook, HookContext, ToolResultAction, ToolResultEvent};

struct LogA2AIds;

impl AgentHook for LogA2AIds {
    async fn on_tool_result(
        &self,
        _context: &HookContext,
        event: ToolResultEvent<'_>,
    ) -> ToolResultAction {
        if let Some(info) = event.tool_context.result::<A2AThreadInfo>() {
            tracing::info!(context_id = ?info.context_id, "a2a turn");
        }
        ToolResultAction::Keep
    }
}
```

## Examples

The first two drive a stub A2A agent on loopback, so they run with no
credentials and no external services.

- [`examples/a2a_tool.rs`](./examples/a2a_tool.rs) — a local agent calling a
  remote one, threading a conversation across turns and observing the remote
  identifiers from a hook.
- [`examples/a2a_agent.rs`](./examples/a2a_agent.rs) — the remote agent as a Rig
  agent: prompting, streaming, and composing as a sub-agent tool.
- [`examples/a2a_client.rs`](./examples/a2a_client.rs) — both surfaces against a
  live A2A server, with an OpenAI-backed agent driving the tool. Needs
  `A2A_AGENT_URL` and `OPENAI_API_KEY`.

## Agent card security

When building from a URL, `A2AClient` fetches the well-known `AgentCard` at
the origin root and rejects a selected interface whose URL points at a different
origin. This prevents a hostile card from redirecting A2A calls, along with any
default HTTP headers on your `reqwest::Client`, to an unrelated host. Trusted
deployments that intentionally publish cross-origin interfaces can opt in with
`A2AClient::builder().allow_cross_origin_interfaces(true)`.

HTTP redirects are disabled for both agent-card discovery and protocol calls,
including when supplying custom HTTP configuration through
`A2AClient::builder().http_client_builder(...)`.

Text projected from A2A responses is capped at 1 MiB, and the tool description
rendered from a remote card at 8 KiB — a card is remote-controlled, and its
description is sent on every completion request.
